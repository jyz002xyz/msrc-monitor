Revision note and correction — July 2026 report

A record of source-data movement observed after this report was published, and a correction to how one of its figures was defined. English first, then Japanese (site convention). 日本語版は こちら。

The published July 2026 report is a point-in-time snapshot frozen on 2026-07-15, and its content has not been changed. This note records changes MSRC made to the underlying data after that snapshot, detected on 2026-07-23. The report was correct as a snapshot; the data has since moved.

Added 2026-08-05 — a correction. Separately from the data movement above, we found a defect in how the figure labelled “core Microsoft” was defined. It reverses one of the report's statements. See Correction — a defect in how “core Microsoft” was defined.

What this note is

Each monthly report is a frozen snapshot of MSRC primary data taken on a specific day. MSRC revises past months after the fact — adding CVEs, re-classifying products, and updating exploitation status. The report itself already discloses this and preserves its snapshot values unchanged. This note is the companion record for the movement observed for the July 2026 data after publication. It does not correct or replace the report.

Effect on two statements in the report

1. "The exploitation-confirmed zero-days were all discovered by humans."

The newly exploitation-confirmed CVE, CVE-2026-58644 (Microsoft SharePoint Remote Code Execution; Critical), has no acknowledged finder — its credit is "uncredited" in the CVRF. As of this note the accurate statement is therefore: three exploitation-confirmed issues were human-discovered; one (CVE-2026-58644) has unknown attribution. The report's original wording no longer holds as-is.

Important — do not read "uncredited" as "AI-discovered."

The absence of an acknowledgment is not evidence of an AI finder. It has several ordinary explanations — internal Microsoft response, a reporter declining acknowledgment, or disclosure routed through an authority (e.g., a national CERT). We do not infer an AI origin from a missing credit. Concretely, the one change in AI-related credit this period (the "kugelblitz" credit, +1) is on a different CVE, not on CVE-2026-58644. This note records the attribution of CVE-2026-58644 as unknown and draws no link to AI.

2. "Once the population is normalized, the peak was June."

Under the revised data, July's core-equivalent count (832) now exceeds June's (frozen 724 / revised 648). Taken at face value this reverses the comparison. But we do not simply rewrite the conclusion to "the peak was July," for a structural reason:

  • At snapshot time the two months were at very different data maturity: July was one day past its Patch Tuesday (2026-07-14 → snapshot 2026-07-15), while June had matured for roughly five weeks. A newer month is systematically undercounted relative to an older one.
  • The revision (+167 core over the following week) is exactly the kind of catch-up a one-day-old month accrues as MSRC keeps adding and re-classifying entries.

The defensible statement is therefore: cross-month count comparisons are only valid when the months are at equal data maturity. This reinforces, rather than contradicts, the report's core argument that raw counts do not reflect the real picture. We do not assert whether the added entries are out-of-band new CVEs or re-classifications of existing ones — the revision record does not carry per-CVE before/after detail, so that breakdown is left undetermined.

Added 2026-08-05: this statement is affected a second time, and more fundamentally, by a defect in the “core Microsoft” definition itself — see the correction below.

A systematic caveat, not a one-off

As long as each month's snapshot is taken the day after its Patch Tuesday, every report structurally undercounts its own month and overcounts the prior month at snapshot time. This is a property of the acquisition schedule, not something specific to July 2026. It is the same effect that makes "this month set a record" and "the prior month was the true peak" both fragile until the data matures.

Correction — a defect in how “core Microsoft” was defined (identified 2026-08-05)

Everything above records movement in MSRC's data. This section is different: it records a defect in our own figure. The number published as “core Microsoft” was produced by a rule that did not do what the label says.

What the defect was. “Core Microsoft” was meant to be the month's CVE records with the Edge/Chromium, Azure Linux (Mariner) and Azure cloud re-listings removed. Which records to remove was decided by matching the vulnerability's title against product-name patterns. Azure Linux package advisories, however, carry the upstream open-source CVE title and contain no product name at all:

  • netfilter: nft_inner: Fix IPv6 inner_thoff desync
  • libexpat before 2.8.2 lacks handler call depth tracking
  • Xorg-x11-server: use-after-free in miext

No pattern could match, so these advisories were counted as core Microsoft. The snapshot was fetched and stored faithfully. The definition of the metric was defective, and the published figure was the value that definition produced. This is not an error in acquiring or recording the data.

Effect on the report. The statement “once the population is normalized, the peak was June” is the one affected. Counting Microsoft-product records only, June is 219 and July is about 575 — July is roughly 2.6 times June. The statement reverses.

Those two numbers are not the same kind of measurement. Read them as follows.

  • June 219 was measured on 2026-08-05 against MSRC's current document for June, using the corrected rule. The same rule applied to the reconstructed 2026-07-15 state also gives 219 — June's Microsoft-product count did not move between the snapshot and now.
  • July “about 575” is a measurement on a reconstruction, not on the frozen document. MSRC's monthly document cannot be retrieved as it stood on 2026-07-15, so that state was reconstructed by keeping only the records whose earliest per-CVE revision date is on or before 2026-07-15. The reconstruction holds 1,164 records against the frozen snapshot's 1,150 (+14, +1.2%). Applying the corrected rule to MSRC's current July document gives 596.

We state this explicitly because presenting a reconstruction as a measurement of the frozen document would repeat, in the correction, the same class of error being corrected.

Why July was the least affected. All seven months were frozen on the same day, 2026-07-15. July alone was one day past its Patch Tuesday (2026-07-14); the other months had matured for one to six months. Azure Linux advisories arrive in bulk starting a few weeks after Patch Tuesday — for June, the most common first-revision date on those records is 2026-06-27 / 2026-06-28. July was fetched before that wave; the older months were fetched after it.

So the published month-over-month “core Microsoft” series was, in effect, a series of how far the Azure Linux backfill had progressed at the moment each month happened to be fetched. The section above already states that cross-month comparison is only valid at equal data maturity. That holds at a deeper level than was known when it was written.

No corrected time series. We are not publishing a corrected month-by-month table. Removing the contamination does not make the months comparable: each month was frozen at a different distance from its own Patch Tuesday, so the maturity problem remains underneath. A corrected series would look authoritative while still carrying the defect the report itself warns about.

What this does not say.

  • Microsoft's own advisories were not removed from anything. The Microsoft-product record count is identical between the reconstructed 2026-07-15 state and 2026-08-05 for all seven months — July being the sole exception at 575 → 596, which is twenty-one advisories published after the snapshot. What moves over time is the Azure Linux portion.
  • Why MSRC includes Azure Linux package advisories in the monthly document, and why that set changes after publication, is unknown to us. We record what the data does; we do not assert why.

The report itself, the frozen snapshot and its figures are unchanged. This note is the record; nothing has been regenerated or restated in the published edition.
