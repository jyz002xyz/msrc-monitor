レポート内の2つの記述への影響

1.「悪用が確認されたゼロデイは、いずれも人間が発見した」

新たに悪用確認された CVE-2026-58644（Microsoft SharePoint リモートコード実行・Critical）は、CVRF 上で謝辞がなく「uncredited（発見者不明）」である。したがって本ノート時点の正確な記述は次のとおり: 悪用確認は3件、うち3件が人間発見、1件（CVE-2026-58644）は帰属不明。 レポートの当初の文言はそのままでは成立しない。

重要 —「uncredited」を「AI が発見した」と読まないこと。

謝辞の不在は AI 発見者の証拠ではない。社内対応、報告者による謝辞の辞退、当局（国の CERT 等）経由の開示など、通常の説明が複数ありうる。謝辞の不在から AI 起源を推論しない。具体的には、今回の AI 関連クレジットの変化（「kugelblitz」クレジット +1）は CVE-2026-58644 とは別の CVE に対するものである。本ノートは CVE-2026-58644 の帰属を不明と記録し、AI と結び付けない。

2.「母集団を揃えると、ピークは6月」

改訂後のデータでは、7月の本体相当件数（832）が6月（凍結 724 / 改訂後 648）を上回る。額面どおりに取ればこの比較は逆転する。しかし、構造的な理由から、結論を単に「ピークは7月だった」と書き換えることはしない:

  • スナップショット取得時点で、両月はデータの成熟度が大きく異なっていた: 7月はPatch Tuesday の翌日（2026-07-14 → スナップショット 2026-07-15）だったのに対し、6月は約5週間成熟していた。新しい月は古い月に比べ、構造的に過小計上される。
  • 今回の改訂（続く1週間で本体相当 +167）は、1日齢の月が MSRC の追加・再分類にともなって取り込む「追いつき」そのものである。

したがって擁護できる記述は次のとおり: 月をまたぐ件数比較は、両月のデータ成熟度が揃っている場合にのみ有効である。 これはレポートの中核的主張「生件数は実像を映さない」を否定するのではなく強化する。追加されたエントリがアウトオブバンドの新規 CVE か、既存の再分類かは断定しない — 改訂記録に per-CVE の before/after が無いため、その内訳は未確定のままとする。

2026-08-05 追記: この記述は、「MS本体相当」の定義そのものの欠陥によって、二重に、かつより根本的な形で影響を受ける。下の訂正を参照。

今回限りではなく、系統的な注記

各月のスナップショットを Patch Tuesday の翌日に取得する限り、どのレポートもスナップショット時点で自月を過小計上し、前月を過大計上する。これは取得スケジュールの性質であって、2026年7月に固有の事象ではない。「今月は記録更新」も「前月こそ真のピーク」も、データが成熟するまではどちらも脆い、という同じ効果である。

訂正 —「MS本体相当」の定義の欠陥（特定 2026-08-05）

ここまでは MSRC 側のデータが動いたことの記録である。本節はそれとは性質が異なり、こちら側の指標の欠陥を記録する。「MS本体相当」として公開した数値は、その名称が意味するとおりの計算をしていない規則で算出されていた。

何が問題だったか。「MS本体相当」は、その月の CVE レコードから Edge/Chromium・Azure Linux（Mariner）・Azure クラウドの再掲載を除いた母集団を意図していた。どのレコードを除くかは、脆弱性のタイトルを製品名のパターンと照合して判定していた。ところが Azure Linux のパッケージ勧告は、上流のオープンソース CVE のタイトルをそのまま持ち、製品名を一切含まない:

  • netfilter: nft_inner: Fix IPv6 inner_thoff desync
  • libexpat before 2.8.2 lacks handler call depth tracking
  • Xorg-x11-server: use-after-free in miext

どのパターンにも該当しえないため、これらの勧告は MS本体相当として数えられていた。スナップショットの取得と記録そのものは忠実に行われている。指標の定義に問題があり、公開した数値はその定義が出した値だったということである。データの取得や記録の誤りではない。

レポートへの影響。影響を受けるのは「母集団を揃えると、ピークは6月」という記述である。Microsoft 製品レコードのみで数えると、6月は 219、7月は 約 575 で、7月が約 2.6 倍となる。この記述は反転する。

この2つの数値は、同じ種類の測定ではない。以下のとおり読まれたい。

  • 6月の 219 は、2026-08-05 に MSRC の現在の6月文書に対し、訂正後の規則で数えた値である。同じ規則を 2026-07-15 時点の再構成に適用しても 219 になる — 6月の Microsoft 製品レコード数はスナップショット時点から現在まで動いていない。
  • 7月の「約 575」は、凍結文書そのものではなく再構成に対する測定値である。MSRC の月次文書は 2026-07-15 時点の姿では取得できないため、CVE ごとの最初のリビジョン日が 2026-07-15 以前のレコードだけを残して同時点を再構成した。この再構成は 1,164 件を含み、凍結スナップショットの 1,150 件に対して +14 件（+1.2%）である。訂正後の規則を MSRC の現在の7月文書に適用すると 596 となる。

これを明示するのは、再構成を凍結文書の測定値として提示すれば、訂正そのものが、いま訂正している誤りと同じ類型を繰り返すことになるためである。

なぜ7月だけ影響が小さかったか。7か月すべてが同じ日、2026-07-15 に凍結されている。そのうち7月だけが Patch Tuesday の翌日（2026-07-14）であり、他の月は1〜6か月成熟していた。Azure Linux の勧告は Patch Tuesday の数週間後からまとまって追記される — 6月の場合、それらのレコードの初回リビジョン日は 2026-06-27・2026-06-28 が最頻である。7月はその波の前に取得され、古い月はその波の後に取得された。

したがって、公開した月次の「MS本体相当」の推移は、実質的に 各月がたまたま取得された時点で Azure Linux の追記がどこまで進んでいたかの推移だったことになる。上記の節では既に「月をまたぐ比較はデータ成熟度が揃っている場合にのみ有効」と述べているが、それは執筆時点で分かっていたよりも深い層で当てはまっていた。

訂正版の時系列は出さない。月ごとの訂正表は公開しない。汚染を取り除いても月間比較は成立しないためである — 各月はそれぞれの Patch Tuesday から異なる距離で凍結されており、成熟度の問題がその下に残る。訂正版の時系列は、権威ある数値に見えながら、レポート自身が警告している欠陥をそのまま抱えることになる。

本節が述べていないこと。

  • Microsoft 自身の勧告が削除されたわけではない。Microsoft 製品レコード数は、2026-07-15 時点の再構成と 2026-08-05 とで7か月すべて一致する — 唯一の例外は7月の 575 → 596 で、これはスナップショット後に公開された21件である。時間とともに動くのは Azure Linux の部分である。
  • MSRC がなぜ Azure Linux のパッケージ勧告を月次文書に含めるのか、またその集合がなぜ公開後に変わるのかは、こちらには分からない。データが何をしているかは記録するが、その理由は断定しない。
