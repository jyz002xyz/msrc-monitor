Executive summary

October 2026's Patch Tuesday is the largest month in this report's observation window (from January 2026). All CVRF went from 1,186 to 1,760, and core Microsoft from 975 to 1,419. Within core, CVEs assigned by Microsoft went from 973 to 1,417 — the same 444 as the rise in core — and 1,411 of the 1,419 were first published at the 13 October release.

Some things did not move with the count. The tier requiring change control fell in core, from 93 to 79. Critical rose across all CVRF from 119 to 174, but fell in core from 114 to 77. Of the 174, 97 sit on the excluded side (Azure Linux package advisories).

There are three zero-days (by Microsoft's definition: confirmed exploited, or publicly disclosed), and one is confirmed exploited. That one is rated Important, not Critical.

Conclusion in one line

The total reached a high for the observation window, while the heavy tier and core Critical both fell. How the count grows does not track how heavy or how dangerous the month is.

Terms: "all CVRF" and "core Microsoft"

All CVRF — every CVE in MSRC's monthly document, including Edge/Chromium, Azure Linux package advisories, and Azure cloud advisories. Press tallies disagree because they cut this population differently.

Core Microsoft — all CVRF with the CVEs whose affected products are all Azure Linux packages, or all Edge/Chromium, removed. Azure cloud advisories stay in core (this month's fourteen azure_cloud CVEs). CVEs whose affected products mix in a Microsoft product also stay in core. The split resolves product identifiers to product names and does not read the CVE title. This month: 1,419 core against 341 excluded — all 341 excluded are Azure Linux. There is not a single Edge/Chromium advisory in this month's CVRF.

What gets exploited is not Critical — four months running

This month's single confirmed-exploited item is CVE-2026-96951 (a security feature bypass in Windows Shell), rated Important. None of the month's 174 Critical items is confirmed exploited.

Every month from July through October that had a confirmed-exploited item had none rated Critical — four months running. May, though, had a Critical one. This does not mean Critical items are not exploited. It means a triage that reads Critical and stops would have missed every confirmed-exploited item across these four months.

The other two are publicly disclosed and not confirmed exploited.

  • CVE-2026-108398 (.NET Framework security feature bypass, Important) — local, by an authenticated attacker.

  • CVE-2026-92707 (MessagePack-CSharp denial of service, Moderate) — MessagePack-CSharp is an open-source component included in Visual Studio, and it sits in core under the classification rule. Its affected products list Visual Studio 2022 and 2026 as well as .NET's MessagePack package for SignalR; because a Microsoft product is in the mix, the rule (mixtures are core) counts it as core. The CVE was assigned by GitHub, not Microsoft.

Count and weight: what did not move together

In a month when the count rose, the axes that stand for response weight did not rise with it.

  • The heavy tier (T2+T3, core) fell from 93 to 79. As a share of core, from 9.5% to 5.6%.

  • Core Critical fell from 114 to 77. That breaks down as 59 remote code execution, 14 elevation of privilege, 3 spoofing and 1 information disclosure — 77 in total.

  • Critical across all CVRF rose to 174 because Critical on the excluded side went from 5 to 97. Of those 97, Linux is the CNA for 89, and all 97 are Azure Linux package advisories.

Read only "all-CVRF Critical", and this looks like a heavy month. Restricted to core, both Critical and the heavy tier are lower than last month. Do not compare Critical counts without checking which population they come from.

Implications and recommended actions

These are recommendations drawn from this report's analysis, not settled regulatory requirements. Specific supervisory expectations should be confirmed against primary sources.

1. What to monitor (continued)

  • Do not use CVE count as a threat indicator. This month it rose 48.4% on last month, yet the heavy tier fell and so did core Critical. The count moved in step with neither defensive load nor risk.

  • Track the tier requiring change control instead. This month it went from 93 to 79 in core. Even the month with the largest total can carry a lighter deployment plan than the month before.

  • But a count is not an amount of work. How far the scope spreads across products changes the effort, and this report does not measure that distribution (the same limit as last month).

2. Decouple triage from the severity label (continued)

  • None of this month's 174 Critical items is confirmed exploited; the one confirmed item is Important. Across July to October, no month's confirmed-exploited items included a Critical one.

  • May, on the other hand, did have a confirmed-exploited Critical. What the four-month record says is that ranking by severity label is unreliable in itself.

  • The destination is unchanged: CISA KEV, EPSS, and asset reachability in combination.

  • Check the population before reading a Critical count. Of this month's 174 all-CVRF Critical items, 97 are Azure Linux advisories.

3. Emergency patch SLA

  • This month's confirmed-exploited item (CVE-2026-96951) was listed in CISA KEV as of the 15 October retrieval. Treat it as an item to start deploying the same day. This report did not retrieve the remediation due date; read it from the KEV entry.

  • Per the vendor's CVSS vector, the preconditions are: reachable over the network, no prior privileges required, attack complexity low — but user interaction is required. The impact is a security feature bypass, and the stated cause is command injection. CVSS base score 8.8; 31 affected products.

  • The temporal metric is "functional exploit exists" (E:F), agreeing with the CVRF's exploitation entry (exploitation detected).

4. Check your own filter (continued)

  • Last issue added "confirmed exploited" as a condition for the KEV/EPSS matched set. This month that set is 1,164 (786 last month); the confirmed-exploited item is in it and was detected as a new KEV listing. That item also carries an external credit, so it would have been in the set under the conditions before last issue as well.

  • A zero-day that is only publicly disclosed is not a condition for matching. This month's CVE-2026-92707 is outside the set and has no EPSS value. The other publicly disclosed item (CVE-2026-108398) is in the set through a different condition. The conditions were not changed in this issue.

  • When matching external threat intelligence against your estate, check every month, with the month's numbers, what has fallen outside the set being matched.

5. Edge/Chromium auto-update (continued)

  • This month's CVRF contains no Edge/Chromium advisory at all (24 last month). Why is not something this report can tell. Absence from the CVRF does not mean Edge shipped no fixes.

  • The point does not depend on the count. Applications that embed Electron/CEF (Teams, Slack, VS Code and others) do not benefit from the browser's auto-update. Enumerating those dependencies in an SBOM matters just as much in a month where the count is zero.

6. Business continuity for AI dependence (continued)

  • Where AI sits in a workflow, treat dependence on a top-tier model as a continuity concern, and make model redundancy and fallback the default.

Appendix: method, sources, accountability record

This appendix records the process behind the conclusions, including hypotheses discarded or corrected along the way, for reproducibility and accountability.

1. Purpose and questions

The question carries over: what can be said about defensive load and actual risk from monthly vulnerability data. This issue additionally checked, before freezing, where in which population the rise came from in a month whose total set a high.

2. Sources

This issue rests on primary data only and cites no press or secondary analysis.

  • MSRC CVRF API v3.0 — monthly security updates as per-CVE structured data, including acknowledgements, severity, exploitation status, affected products, CVSS vectors and FAQs.

  • CISA KEV catalog — the catalog of vulnerabilities known to be exploited.

  • FIRST EPSS — the estimated probability that exploitation activity will be observed within 30 days.

3. How the data was acquired

Primary data was fetched in the acquisition environment and frozen two days after Patch Tuesday (06:43 on 15 October), the same distance as August and September. Against the daily fetch of the day before (07:01 on 14 October), core (1,419), credited (1,334), Critical (174 all / 77 core), the heavy tier and the three zero-days were unchanged. The total rose by one, from 1,759 (CVE-2026-95838 on the excluded side, first published 14 October). What moved was the severity of one core CVE (unrated → Important) and a few finder buckets (external 998 → 1,000, anonymous 169 → 167). The day-before fetch computed product categories with the old classification, so categories were not compared. KEV was retrieved on the day of the freeze (15 October). The EPSS date is 2026-10-14 (FIRST dates by UTC, and 14 October was the latest available at retrieval).

4. Method, in sequence

  1. Primary data fetched two days after Patch Tuesday.

  2. Compared with the previous day's daily fetch: core, credited, Critical, the heavy tier and zero-days had not moved. The total rose by one on the excluded side, and severity and finder buckets moved by a few (section 3).

  3. With the total up 48.4% on last month, the rise was checked before freezing — core or excluded, by CNA, first-revision date, product category and product (section 5, discarded 2).

  4. Frozen.

  5. KEV and EPSS retrieved for this month's matched set.

  6. For the three zero-days, the exploitation entries, CVSS vectors and descriptions were read in the original CVRF.

  7. The recount behind last issue's Table 1 key point was re-run and gave the same breakdown (section 5, correction 1).

Record 3: two CVEs on the population boundary. Two CVEs are in core by the rule but cannot be called core Microsoft without qualification.

  • CVE-2026-92707 (MessagePack-CSharp) — an advisory for an open-source component included in Visual Studio, assigned by GitHub. Its affected products mix Visual Studio and .NET packages, so the rule "mixtures are core" puts it in core. It is also one of this month's zero-days (publicly disclosed).

  • CVE-2026-62840 (Linux Kernel elevation of privilege) — its affected products are third-party Linux distributions and Microsoft's MANA network driver. It is not an Azure Linux package, so it is in core.

Without the two, core is 1,417, and nothing in this issue reads differently. The no-impact item in correction 1 (CVE-2026-34182, OpenSSL) has the same shape: it mixes Visual Studio and Azure Linux packages and sits in core. The October issue was frozen under the same rule as last issue (v2). The question of the rule is recorded as material for review; it is not reflected in this issue's figures.

Record 4: a zero-day that is only publicly disclosed is not in the KEV/EPSS matched set. The condition is "heavy tier (T2/T3) or Critical or externally credited, or confirmed exploited"; whether something is publicly disclosed is not part of it. This month's CVE-2026-92707 meets none of these, is outside the set, and has no EPSS value. The confirmed-exploited CVE-2026-96951 is in the set and was detected as a new KEV listing.

Continuation 5: exploitation status within one document. Last issue recorded that, among confirmed-exploited CVEs, the CVSS temporal metric agreed with Threats for some and not for others. This month's confirmed-exploited item (CVE-2026-96951) carries "functional exploit exists" (E:F), agreeing with Threats' "exploitation detected". One agreeing item does not make the field usable. This report's exploited flag continues to derive from Threats.

Continuation 6: do not attach circumstantial evidence to a named entity. The July issue asserted that "Kugelblitz" was a particular in-house AI tool and withdrew it against primary sources. That discipline holds. Nothing is claimed about activity stopping or continuing now that the name has been at zero for two months.

6. What the conclusions rest on, and the limits

Relied upon (high confidence)

  • The frozen figures are machine aggregations of primary data; against the previous day's daily fetch, core, credited, Critical, the heavy tier and zero-days did not move (severity and finder buckets moved by a few).

  • This month too, the population split is product-identifier based and every product identifier resolved (zero unresolved). All 341 excluded are Azure Linux; Edge/Chromium is zero.

  • Where the rise in core sits (CNA, first-revision date, product category) was checked against the CVRF of the same release as the frozen figures.

  • The preconditions of the confirmed-exploited item (network, no prior privileges, user interaction required, low attack complexity) come from the CVSS vector in the CVRF.

Limits (undetermined; treat with care)

Terms
CVRF
The machine-readable vulnerability feed Microsoft publishes each month (MSRC CVRF v3.0) — this report's primary data.
Full CVRF / core Microsoft (re-listings)
“Full CVRF” is every CVE record the feed returns for a month, which mixes in Edge/Chromium (fixed by Google and re-listed by Microsoft), Mariner (Azure Linux) and Azure cloud services. “Core Microsoft” is the same month with those re-listings excluded. The two populations are reported side by side.
Zero-day
In this report, a CVE that Microsoft's data flags as exploited, or as publicly disclosed, or both.
Confirmed exploitation
Microsoft's own exploitation flag is set for that CVE. This is a separate source from CISA KEV, and the two can disagree in either direction.
KEV
CISA's Known Exploited Vulnerabilities Catalog — vulnerabilities CISA has confirmed as exploited. Cross-vendor listings are recorded in the Cross-vendor KEV/EPSS section of this site.
EPSS
The probability that exploitation activity will be observed within 30 days (0 to 1). It is not a severity score.
